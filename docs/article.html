Hands-on networking lab · VPP 26.10

Using VPP to Explore and Troubleshoot Ultra Ethernet

Build a small Ultra Ethernet Transport (UET) lab, watch its packets inside VPP, and deliberately introduce network problems. Use VPP's counters and traces to explain each failure and check that the fix works.

An application reports that a transfer is slow or has failed. Finding the cause starts with seeing what happened to its packets. In this article, we use VPP as an observable, configurable network around two UET test applications.

VPP is a software packet processor. It can forward traffic, show the steps a packet took, and simulate network conditions such as loss and delay. A counter tells us how often an event occurred; a trace records what happened to an individual packet.

We will begin with a working exchange, then change one network condition at a time. By the end, you will have used VPP to watch UET recover from packet loss, explain a transfer blocked by an undersized network path, and identify retries caused by delayed responses. We will also distinguish reordered packets from lost ones and use a VPP QoS policy to protect UET exchanges from competing traffic.

Build a small network you can inspect

Everything runs on one Linux machine. Each application exchanges UET packets with a VPP instance through shared memory. VPP A and VPP B communicate over a virtual link, implemented by VPP's memif interface. This gives us a network whose behaviour we can change and inspect.

The UET protocol runs in the applications. VPP handles their network packets and provides the monitoring, tracing and fault injection used in the experiments.

The commands below use Ubuntu on an x86-64 machine with at least four available logical CPUs and sudo access. The downloadable scripts build the test applications and VPP 26.10, including the UET trace decoding shown below. The lab README contains the full setup details.

Download and unpack the lab files. From their directory, build and start the network:

sudo apt-get update
sudo apt-get install -y git build-essential python3
export UET_LAB_ROOT="$HOME/uet-observability"
UET_LAB_INSTALL_DEPS=1 bash build.sh "$UET_LAB_ROOT"
sudo python3 lab.py --root "$UET_LAB_ROOT" up

Keep that terminal for running the tests. In another terminal, open VPP A's CLI—its interactive command line. Use console b in a third terminal to inspect VPP B:

sudo python3 lab.py --root "$UET_LAB_ROOT" console a

The prompt becomes vpp#. These commands ask VPP about the running plugins, its processing threads, the virtual link and the IP configuration:

set terminal pager off
show plugins
show threads
show memif
show interface address
show ip fib
show ip neighbors

The first useful checkpoint is admin-up connected in show memif: the two VPPs have established their virtual link. show interface address should show 198.18.0.1 on A and 198.18.0.2 on B. The route and neighbor commands show how each VPP reaches the other endpoint. We check this before interpreting any UET failure.

Start with a working UET exchange

Run a short test from the original terminal:

sudo python3 lab.py --root "$UET_LAB_ROOT" run --iterations 20

The client sends a 4 KiB message and waits for a reply. The application repeats this 20 times with one buffer per message, then 20 times with several buffers per message: 40 exchanges in total. Both applications check the data and finish successfully.

While the test runs, use show uet in VPP A's console. Here are selected fields from a sample taken while the client was still connected:

state enabled

Read TX as packets submitted by the application to VPP, and RX as packets received from the network and handed to the application. In this sample, 203 packets have travelled in each direction.

The application and VPP exchange packets through shared queues, called rings. invalid-requests 0 and the zero ring-full counters show that the plugin has accepted the submissions without a queue-capacity error. rx-releases 203 and rx-outstanding 0 show that the application has returned all 203 received buffers at this point.

tx-completions records acceptance at the application/VPP boundary. To confirm delivery to the other endpoint, we also need the received responses and the application's result. This distinction will explain the MTU failure below.

provider-ready yes means the application is connected. Once it exits, provider-ready no is expected. The scripts also save show uet every 500 ms, so you can review the changing counters after a test.

Experiment 1: drop packets and watch UET recover

First, create a fault whose cause we know. VPP's nsim plugin simulates network conditions; here we ask it to discard about one percent of the packets leaving VPP A:

sudo python3 lab.py --root "$UET_LAB_ROOT" run --loss 0.01

This longer test runs 1,000 exchanges in each of the application's two buffer modes. In our recorded run, VPP dropped 99 packets and both applications still completed. To understand how they recovered, inspect VPP A:

show interface features memif1/0
show nsim
show errors
show trace paths
show trace path 3 max 1

A VPP node is one processing step. show trace paths groups packets by the steps recorded in their traces. Pick the path that ends at the simulated loss, then use its index with show trace path; our index was 3, and yours may differ.

Two UET fields make the packet easy to follow: PSN is its packet sequence number, and RETX 1 marks a retransmission. The same PSN appears in these abridged records:

VPP A, original request:
  PDS ROD_REQ RETX 0 SPDCID 65 DPDCID 65 PSN 505542063
nsim-output-feature
  NSIM: dropped, simulated network loss

VPP A, retransmission:
  PDS ROD_REQ RETX 1 SPDCID 65 DPDCID 65 PSN 505542063

VPP B, receive:
  UET RX: ... disposition delivered
  PDS ROD_REQ RETX 1 SPDCID 65 DPDCID 65 PSN 505542063

We can now follow the recovery: VPP A drops the original packet, UET sends the packet again with RETX 1, and VPP B reports disposition delivered. Matching the source IP and PSN, together with the delivery-context identifiers SPDCID and DPDCID, links the records across the two VPPs. The numerical PSN will vary between runs.

This is the debugging value of the trace: it connects a known network fault to the transport's reaction and the eventual delivery.

Use show trace max 4000 to display more of the saved packets; plain show trace displays only 50 per thread. In show errors, read the Reason column and look for Network loss simulation drop packet. The same output includes normal activity counters such as “Packets buffered”. The explicit nsim drop record identifies this injected fault; these packets are freed directly by the simulator.

Experiment 2: explain why a larger transfer fails

Now change the maximum size of an IPv4 packet that VPP can send on the link. This limit is the MTU, or Maximum Transmission Unit. Set it to 576 bytes and try a small message:

sudo python3 lab.py --root "$UET_LAB_ROOT" run --mtu 576 --size 64 --iterations 20

The 64-byte messages pass. Try the original 4 KiB message over the same path:

sudo python3 lab.py --root "$UET_LAB_ROOT" run --mtu 576 --size 4096 --iterations 1 --deadline-s 8

The script applies VPP's set interface mtu ip4 576 memif1/0 command on both sides, while the application still uses a configured MTU of 1500. This deliberately creates a mismatch. The command is expected to fail: the client reaches UET's retry limit and reports an I/O error. The script then stops the waiting server.

An application error tells us the exchange failed. show uet gives us a first clue about where to investigate:

tx-requests 404
invalid-requests 0
tx-completion-ring-full 0
tx-packets 404
tx-completions 404
rx-delivered 0
rx-ring-full 0
rx-outstanding 0

All 404 submissions, including retries, were accepted by the plugin. The queue-full counters are zero, and no UET response has arrived. To find what happened after submission, inspect the interface and packet path:

show interface memif1/0
show errors
show trace paths
show trace path 1 max 1

Choose the drop-path index listed by your own show trace paths. show errors gives us a specific reason:

   Count                  Node                              Reason               Severity
       404             ip4-input                 ip4 MTU exceeded and DF set       error
       404           ip4-icmp-error                 error message dropped          error

The trace shows the packet's size and the limit it encounters:

uet-input
  UET TX: ... ip4/native length 1108 ... disposition routed

  flags DONT_FRAGMENT

  ... ipv4 via 198.18.0.2 memif1/0: mtu:576 ...

UET has already divided the 4 KiB message into smaller packets. The packet in this trace is 1,108 bytes, which still exceeds the link's 576-byte MTU. DONT_FRAGMENT tells VPP that this IPv4 packet must not be split into further fragments.

The trace locates the rejection at the IPv4 forwarding step. UET keeps retrying a packet that is too large for this path. VPP has given us both the cause and the configuration to change.

Restore the MTU to 1500 and repeat the transfer. After this deliberately failed test, restart the lab to begin with fresh applications and VPP instances:

sudo python3 lab.py --root "$UET_LAB_ROOT" down
sudo python3 lab.py --root "$UET_LAB_ROOT" up
sudo python3 lab.py --root "$UET_LAB_ROOT" run --mtu 1500 --iterations 20

The corrected VPP setting is set interface mtu ip4 1500 memif1/0. The same 4 KiB transfer now completes, the MTU errors stay at zero, and the retry warnings disappear. Reopen the CLI consoles after restarting VPP to inspect the new run.

We have used a VPP configuration change to reproduce the failure, its trace to explain the rejection, and a second run to verify the fix. The UET library code is unchanged.

Experiment 3: add delay and investigate retries without loss

A retry can also happen when a packet arrives successfully but its response takes longer than the sender is prepared to wait. UET uses acknowledgements, or ACKs, to track delivery. Its retry timer determines when it sends a packet again.

The 20 ms delay is deliberately large: we want it to exceed the reference software's default 5 ms retry timer so the effect is easy to observe. That timer is configured in milliseconds. For scale, the UEC congestion-control specification uses an illustrative 12 us base RTT. Our experiment creates a strongly degraded path to demonstrate the mechanism. The 100 ms value used later is an alternative UET retry timeout.

Use VPP to add 20 ms of delay in each direction, with no configured loss, while retaining that 5 ms retry timeout:

sudo python3 lab.py --root "$UET_LAB_ROOT" run --delay-ms 20 --reverse-delay-ms 20 --tx-timeout-ms 5 --iterations 20

This asks VPP's simulator to apply the following setting on each side:

set nsim delay 20 ms bandwidth 1 gbit packet-size 1500 drop-fraction 0

show nsim confirms the delay, and show errors reports no simulated-loss or buffer-exhaustion drops. Yet the application reports retries. These records from VPP A show the original send, a retry, and the returning ACK on the same clock:

00:00:06:287479: uet-input
  198.18.0.1 -> 198.18.0.2 PDS ROD_REQ RETX 0 SPDCID 65 SYN 1 PSN 221390863

00:00:06:292351: uet-input
  198.18.0.1 -> 198.18.0.2 PDS ROD_REQ RETX 1 SPDCID 65 SYN 1 PSN 221390863

00:00:06:327616: uet4-ip-input
  198.18.0.2 -> 198.18.0.1 PDS ACK RETX 0 SPDCID 65 DPDCID 65 CACK_PSN 221390863

The original's ACK returns about 40 ms after the initial send, matching the delay we introduced in the two directions. The retry occurred much earlier. Its PSN is unchanged, and the ACK's CACK_PSN acknowledges that same sequence number. The SYN field marks the initial setup of packet delivery.

We can now explain the symptom: the retry timer expires before the network has time to return the ACK. On ACK packets, the RETX field describes the request being acknowledged.

Keep show uet open while experimenting. In this run, a sample taken during the transfer showed:

Test the diagnosis by removing the delay in VPP and repeating the same work with the original UET timeout:

sudo python3 lab.py --root "$UET_LAB_ROOT" run --delay-ms 0.1 --reverse-delay-ms 0 --tx-timeout-ms 5 --iterations 20

The script restores a 100 us delay from A to B and removes the delay feature on the return path. Verify that change with show interface features memif1/0: it shows which features are actually applied to the packets.

As another check, we kept the long network delay and increased UET's existing timeout setting to 100 ms with --tx-timeout-ms 100. Both controls eliminate the retries:

The useful result is the connection between network behaviour and UET's response. VPP let us create the delay, observe the late ACK, and confirm that removing the delay removed the retries.

Experiment 4: distinguish a late packet from a lost packet

Packets can arrive in a different order even when the network drops none of them. Before interpreting a retry or an ordering-related response, we need to establish what actually reached the receiver.

Keep the 4 KiB messages and run a clean control, then ask VPP A to delay a quarter of its packets by up to one additional millisecond:

sudo python3 lab.py --root "$UET_LAB_ROOT" run --iterations 30
sudo python3 lab.py --root "$UET_LAB_ROOT" run --iterations 30 \
    --reorder-fraction 0.25 --reorder-delay-ms 1 --trace-packets 4000

The launcher keeps the base delay at 100 us, the random-loss probability at zero and UET's retry timeout at 5 ms. Check the configured cause in VPP A:

show nsim
show errors
show trace paths

Our run counted 100 packets sent through the late-reorder wheel and no nsim drops. Now inspect show trace max 8000 on VPP B. These two abridged records show original requests arriving in the opposite order to their packet sequence numbers:

00:00:06:109019: uet4-ip-input
  UET RX: ... disposition delivered
  PDS ROD_REQ RETX 0 SPDCID 65 SYN 1 PSN 1954782285

00:00:06:109250: uet4-ip-input
  UET RX: ... disposition delivered
  PDS ROD_REQ RETX 0 SPDCID 65 SYN 1 PSN 1954782282

The lower PSN arrives 231 us after the higher one. Both have RETX 0, so this pair demonstrates reordered original requests. VPP's receive disposition means delivery to the application-facing shim; the UET transport still decides how to handle their order.

The collector found 43 such backward steps in the sampled arrival sequence, compared with zero in the clean control. Both applications completed 30 exchanges in each buffer mode and logged zero PDS retransmission warnings. The client also logged No Match and Bad Generation semantic responses; those are retained in the application logs and are separate from the PDS retry count.

This experiment uses the application's existing ROD mode. It demonstrates observed packet arrival and the reference stack's outcome under reordering. A RUD comparison would need an application explicitly configured for that delivery mode.

Experiment 5: congest the return path and test a QoS policy

A request may reach its destination while its acknowledgement waits behind other traffic on the way back. VPP lets us inspect that return path and test whether controlling competing traffic changes the result.

For this experiment, use 64-byte application messages. Configure VPP B's nsim output as a queue with a nominal rate of 40 Mbit/s, a 20 ms buffer and 100 us propagation delay. First run it without competing traffic:

sudo python3 lab.py --root "$UET_LAB_ROOT" run --size 64 --iterations 30 \
    --reverse-delay-ms 0.1 --reverse-bandwidth-mbps 40 --reverse-buffer-ms 20

Next add 5,000 ordinary UDP packets per second, generated by VPP B through its pg0 interface:

sudo python3 lab.py --root "$UET_LAB_ROOT" run --size 64 --iterations 30 \
    --reverse-delay-ms 0.1 --reverse-bandwidth-mbps 40 --reverse-buffer-ms 20 \
    --background-pps 5000

The UDP packets and UET's return packets share B's memif output and nsim queue. No UDP generator runs inside the UET application. Inspect VPP B:

show packet-generator verbose
show interface features memif1/0
show nsim verbose
show errors
show uet
show trace max 8000

show nsim verbose identifies the queued model, its rate and its buffer. show errors reports packets dropped when that queue fills. The background packets are discarded at VPP A; they never enter the UET transport. The complete snapshots retain those separate receive-side discard counters too.

For an ACK that did get through, B's native trace shows where it waited:

00:00:16:029537: uet-input
  PDS ACK RETX 0 SPDCID 65 DPDCID 65 CACK_PSN 1494962252
00:00:16:049845: nsim-wheel

The interval between these two graph timestamps is 20.308 ms, already longer than the 5 ms retry timeout. Both timestamps belong to VPP B, so this calculation needs no clock synchronization between the two VPPs. The trace localizes waiting on the return path; the queue-full counter separately establishes actual loss under overload.

Now apply a QoS policy that limits only the background ingress to 6 Mbit/s:

sudo python3 lab.py --root "$UET_LAB_ROOT" run --size 64 --iterations 30 \
    --reverse-delay-ms 0.1 --reverse-bandwidth-mbps 40 --reverse-buffer-ms 20 \
    --background-pps 5000 --background-policer-mbps 6

In this third run, the launcher applies these native VPP commands:

policer add name background type 1r2c rate kbps cir 6000 cb 6000 conform-action transmit exceed-action drop violate-action drop
policer input name background pg0

The policer admits traffic within its rate and burst allowance and drops excess background packets before they reach the shared output queue. UET uses its separate shared-memory ingress, so its ACKs and replies bypass this policer. This is ingress load control; there is no strict-priority output scheduler in this example.

While the test runs, inspect show interface features pg0 and show policer name background. The saved snapshots include the policy before the launcher removes it. An abridged sample shows that background traffic is still admitted:

The policer moves the deliberate background drops to ingress, removes the output queue overflows and restores prompt UET feedback. These are observations from counters and sampled traces, rather than an assumption that a successful application must have experienced a healthy network. An additional comparison with the applications restricted to the same four CPUs as VPP showed the same effect.

The nsim queue uses a nominal 1,500-byte service cost for every packet, including small ACKs. Its low rate makes the effect visible on a normal computer; the table measures this software experiment, not production-fabric latency. Both ACKs and echoed data share the return path, so the result covers the whole return traffic stream.

Persistent overload can exhaust the retry budget on a smaller machine, as it did in our ARM64 VM. If an application fails, recreate the lab before the next manual run. The automated comparison records that outcome and restarts the lab before testing the QoS repair:

sudo python3 transport_scenarios.py --root "$UET_LAB_ROOT" --scenario qos --repeats 3

The useful debugging sequence is visible throughout: find the waiting or dropping node, correlate the UET packets, apply a specific network policy, and check the same observations again.

Start with show uet to see whether the application is submitting and receiving packets. Use show errors and traces to find where packets are discarded or delayed. Then change the suspected network condition and rerun the exchange.

For a wider view, show runtime and show threads show where VPP is doing the work, and show buffers shows buffer-pool usage. These observations help you decide whether to investigate the packet path, processing resources or the application's interaction with VPP.

The counters cover the full run, while the saved traces contain a limited selection of packets. Re-arm tracing when its budget is exhausted. Exact counts vary, and recording traces can affect timing; use this lab to investigate behaviour rather than measure throughput.

Type quit to leave the consoles, then stop the isolated lab:

sudo python3 lab.py --root "$UET_LAB_ROOT" down

Looking ahead: hosting the UET transport inside VPP

A further architecture is under study: integrating the reference UET library into a VPP plugin so that VPP itself hosts the transport. In today's lab, VPP delivers packets through shared memory to an external UET application, which runs the transport protocol.

The proposed design would bring the reference implementation's message handling, reliable packet delivery and transport security into the VPP process, with the goal of reusing the library unchanged. It would extend the packet-level visibility demonstrated here toward closer integration with the transport engine itself.

The lab uses the public UEC reference implementation, VPP 26.10 and libfabric 1.20.1. The test application calls the reference UET API directly; libfabric provides types and support functions.

The download includes an application addressing addition and trace extensions for the UET and nsim plugins. The UET transport library and NIC shim remain unchanged. The README documents these additions, the exact source revisions and the tested environment: Ubuntu 26.04.1 on x86-64 Linux. The added reordering and QoS scenarios were also exercised in an ARM64 Linux VM; its overloaded run exhausted the retry budget, while its reordered and policed runs completed. A fresh minimal-VM installation has not been validated. Published evidence has lab-specific identities, machine names, home paths and runtime memory addresses anonymized. Raw packet hexdumps are omitted. Protocol sequence numbers, counters, timestamps and application outcomes are retained.
